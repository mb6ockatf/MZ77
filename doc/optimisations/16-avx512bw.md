# #16 AVX-512BW match compare

Measured on hppavillion (Intel Core i3-1115G4, Tiger Lake), the only
machine here with AVX-512.  On debian (Zen 2, no AVX-512) the program
falls back to the 8-byte loop of #15; that run only shows that the
fallback costs nothing.

## Before

After #15 a candidate match is compared 8 bytes per step: two 64-bit
loads, an XOR, a branch, and `ctz` on the first non-zero XOR.  A
258-byte match takes 32 steps and 2 single-byte compares.

## Change

* `match_length_avx512` compares 64 bytes per step:
  `_mm512_loadu_si512` both sides, `_mm512_cmpneq_epi8_mask` gives a
  64-bit mask of unequal bytes, `ctz` of the mask is the match length.
  The last partial block uses masked loads
  (`_mm512_maskz_loadu_epi8`), which never touch the bytes outside the
  mask, so the limit is never overrun.  A 258-byte match takes 5 steps.
* The whole compression loop is compiled twice from one `always_inline`
  body: `compress_word` (plain x86-64) and `compress_avx512`
  (`__attribute__ ((target ("avx512bw,avx512vl")))`), so the AVX-512
  match routine is inlined into its loop and there is no indirect call
  per candidate.
* `lz77_compress` picks one at run time with `__builtin_cpu_supports`,
  once per file.  The program still builds for and runs on any x86-64
  CPU, and the strict CI build is unchanged.  On other architectures
  the AVX-512 code is not compiled at all.
* `MZ77_MATCH=word` in the environment forces the portable loop; the
  benchmark uses it to measure both paths on the same machine.

## Correctness

`make check`, strict `distcheck` in release and debug, and archives
byte-identical to the baseline, with the AVX-512 path and with
`MZ77_MATCH=word`, for the edge-case files (empty, 1..9 bytes, 255,
256, 4095..4097, 65535..65537, 200 KB, random and repetitive), 1.5 MB
slices of dickens, mozilla, x-ray, mixed and zeros, the files in
test/input and every corpus file (raw/archives.sha256 of both machines
and of hppavillion's x-05-word).  The benchmark decompresses every
archive and compares it with the input.

## Complexity

Same bound, O(n * C * M) worst case; the match compare does at most 5
steps instead of 32 steps and 2 single-byte compares.  A candidate
that differs in its first bytes costs one 64-byte step instead of one
8-byte step, which is a little more work.

## Results

Whole corpus, sums of per-file medians (bench/log/*/SUMMARY.md):

| machine | | before (#15) | after | speed-up | vs baseline |
|---|---|---|---|---|---|
| hppavillion (i3-1115G4), AVX-512 | compression | 5.986 s | 4.824 s | **1.24x** | **3.26x** |
| | decompression | 1.308 s | 1.171 s | (unchanged) | 2.14x |
| debian (Ryzen 7 5700U), fallback | compression | 3.875 s | 3.920 s | 0.99x | 2.58x |
| | decompression | 0.928 s | 0.923 s | (unchanged) | 2.24x |

Cycle counts for compressing the whole corpus
(bench/log/*/05-avx512bw/raw/followup/): on hppavillion 18.2 G with
#15, 18.6 G for the portable path of #16 and 14.9 G for its AVX-512
path (1.22x fewer than #15, with 19 % fewer instructions); on debian
16.3 G with #15 and 16.2 G with the fallback.

The gain is smaller than #15's because the 8-byte loop had already
removed most of the per-byte work; the 64-byte step only helps on
matches longer than 8 bytes.  mixed.dat, with long repeats, takes
1.43x fewer cycles, nci 1.25x, the text-like files about 1.15x, most
other silesia files 4 % to 10 %; random.dat, whose candidates differ
in the first bytes, takes 4 % more.  On the fallback path the 1 % in
wall time on debian is noise: the release build takes 0.4 % fewer
cycles than #15.  On hppavillion the portable path costs about 2 %
more cycles than #15 with the same instructions, a code-layout effect
that only matters with `MZ77_MATCH=word`.  Decompression is not
touched.  The details are in
bench/log/hppavillion/05-avx512bw/EXPLANATION.md,
bench/log/hppavillion/x-05-word/EXPLANATION.md and
bench/log/debian/05-avx512bw/EXPLANATION.md.
